Manual del Aprendiz: Bases de Datos NoSQL y Esquemas JSON/BSON

Este documento constituye tu guía técnica oficial para comprender los fundamentos de bases de datos documentales, diseñar colecciones eficientes en MongoDB y estructurar con rigor pedagógico la evidencia GA6-220501096-AA1-EV03 para el Corte 1.

1. El Paradigma NoSQL y el Modelo Orientado a Documentos

Durante décadas, las bases de datos relacionales (RDBMS como MySQL, PostgreSQL u Oracle) dominaron el software empresarial gracias a la rigidez del modelo tabular y el estándar SQL. Sin embargo, con el nacimiento de aplicaciones web hiperconectadas, comercio electrónico masivo y arquitecturas orientadas a eventos (Node.js, React), surgió la necesidad de almacenar datos sin un esquema prefijado que limite la evolución ágil del producto.

Definición Clave: Una base de datos NoSQL Documental organiza la información en unidades autónomas llamadas documentos, que se agrupan en colecciones. A diferencia de las tablas SQL, cada documento puede tener campos y tipos de datos diferentes, adaptándose a entidades complejas sin requerir migraciones de esquema continuas.

Equivalencia Terminológica RDBMS vs MongoDB:

Modelo Relacional (MySQL) Modelo Documental (MongoDB) Descripción en el Proyecto
Base de Datos (Database) Base de Datos (Database) Contenedor global del proyecto (ej. techstore_nosql).
Tabla (Table) Colección (Collection) Agrupación de documentos afines (ej. colección usuarios).
Fila / Registro (Row) Documento BSON (Document) Objeto individual que contiene la información completa de la entidad.
Columna (Column) Campo (Field) Par clave-valor (ej. "email": "carlos@sena.edu.co").
Llave Primaria (PK) _id (ObjectId) Identificador único autogenerado de 12 bytes hexadecimales.

2. Estructuras de Datos: Diferencia entre JSON y BSON

Para trabajar con éxito en MongoDB, debes comprender que JSON es el formato de intercambio visual que utilizas en tu editor y en tu frontend React, pero BSON (Binary JSON) es el formato de serialización interna que procesa el motor de MongoDB.

¿Por qué BSON? JSON plano no distingue entre un número entero (32 bits) y un decimal flotante, ni tiene soporte nativo para fechas o identificadores criptográficos. BSON soluciona esto introduciendo tipos de datos enriquecidos:
  • ObjectId: Cadena de 24 caracteres hexadecimales compuesta por timestamp de creación (4 bytes), identificador de máquina (5 bytes) y contador incremental (3 bytes).
  • ISODate: Fecha en formato universal UTC (ej: ISODate("2026-10-20T18:30:00Z")) que permite indexación y cálculos temporales.
  • Subdocumentos Embebidos: Un objeto anidado dentro de otro campo (direccion: { ciudad: "Garzón" }).
  • Arreglos (Arrays): Listas de elementos indexables (ej: roles: ["CLIENTE", "ADMIN"]).

3. Patrones de Diseño NoSQL: Embebido vs Referenciado

El error más común del aprendiz que viene del mundo SQL es diseñar 10 colecciones separadas y llenarlas de identificadores foráneos. En MongoDB, debes aplicar la Regla de Oro: "Datos que se consultan juntos, se guardan juntos".

Límite de Tamaño: En MongoDB un documento BSON no puede superar los 16 MB. Si una relación de 1 a Muchos puede crecer indefinidamente (ej: millones de registros de telemetría de un sensor), NO la embebas; usa referencias mediante _id.

Ejemplo A: Patrón Embebido (Embedding — Subdocumento 1:1 o 1:Pocos)

El perfil del usuario y su dirección de envío siempre se leen juntos en el checkout. No se crea una tabla separada; se incrusta el subdocumento:

// Colección: usuarios (Documento con Subdocumento Embebido) { "_id": ObjectId("67158f918e77a1a4b9240101"), "nombre": "Carlos Pérez", "email": "carlos.perez@techstore.co", "direccion": { // Subdocumento 1:1 "ciudad": "Garzón", "departamento": "Huila", "calle": "Carrera 10 # 14 - 28" }, "telefonos": ["3101234567", "3159876543"] }

Ejemplo B: Patrón Referenciado (Referencing — Relación 1:Muchos Ilimitados)

Un usuario puede comprar cientos de veces a lo largo de los años. Para no inflar el documento del usuario, las compras se guardan en la colección ordenes con una referencia por id_usuario:

// Colección: ordenes (Referencia a la colección usuarios) { "_id": ObjectId("67158f918e77a1a4b9240301"), "numero_orden": "ORD-2026-0091", "id_usuario": ObjectId("67158f918e77a1a4b9240101"), // Referencia foránea "total": 5200000.00, "estado": "PAGADA", "fecha": ISODate("2026-10-20T20:15:00Z") }

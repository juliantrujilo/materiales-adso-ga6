1. Ficha Técnica y Contexto Normativo en Guía 6

En el ciclo de vida del software, la base de datos representa el cimiento sobre el cual descansan las transacciones, la consistencia y la seguridad del sistema. Un diseño relacional deficiente ocasiona redundancias masivas, anomalías de inserción, actualización y borrado que degradan la experiencia de usuario.

En esta primera sesión técnica abordamos la Actividad de Aprendizaje GA6-220501096-AA1 (*Crear un modelo de base de datos, con base a los requerimientos del cliente*), evaluando el RAP 220501096-02 (*Construir la base de datos para el software a partir del modelo de datos*).

Las 2 Evidencias a Desarrollar:
• AA1-EV01 (Conocimiento): Resolución de problemas aplicando el modelo relacional, cardinalidad y normalización (Documento PDF con 1FN, 2FN y 3FN).
• AA1-EV02 (Desempeño): Modelo entidad relación de caso (Diagrama E-R en herramienta CASE formal con diccionario de datos).

3.2. Introducción Técnica Modelo

📝 Introducción Técnica Contextualizada
El presente informe técnico expone el proceso de diseño conceptual, lógico y estructuración relacional de la base de datos para el proyecto formativo TechStore Pro React, correspondiente a la plataforma web de comercio electrónico desarrollada durante la Fase 3: Ejecución de la Tecnología en Análisis y Desarrollo de Software (ADSO — Ficha 3389010). A través de la aplicación metódica de las reglas de normalización (Primera, Segunda y Tercera Forma Normal), se transforma un esquema plano con redundancias y riesgos de inconsistencia en una estructura de datos robusta, escalable y optimizada. Asimismo, se determinan con precisión las claves primarias (PK), claves foráneas (FK) y cardinalidades relacionales, garantizando la integridad referencial y preparando el sistema para su posterior implementación física en el motor de base de datos MySQL.

4. Paso a Paso Didáctico para la Evidencia EV01

Desarrollo guiado del caso real de facturación del e-commerce TechStore Pro React:

Paso 1: Estado Inicial No Normalizado (0FN)

Una sola tabla masiva donde se almacena todo el ticket de compra:

Factura_Global ( id_factura, fecha_emision, cedula_cliente, nombre_cliente, email_cliente, telefono_cliente, direccion_cliente, ciudad_cliente, productos_comprados [id_prod, nombre_prod, categoria_prod, precio_prod, cantidad], subtotal, iva, total_factura, metodo_pago, estado_pago, referencia_transaccion )
Las 3 Grandes Anomalías Relacionales Detectadas en 0FN:
• Anomalía de Inserción: No se puede registrar un cliente nuevo si aún no ha comprado nada (los campos de factura quedarían en NULL, rompiendo la PK). Tampoco se puede registrar un producto si aún no se ha vendido.
• Anomalía de Actualización: Si un cliente cambia su celular, hay que actualizarlo en cada una de sus compras históricas. Un solo olvido causa inconsistencia en la base de datos.
• Anomalía de Borrado: Si se cancela la única compra de un cliente, se borran accidentalmente todos sus datos de contacto del sistema.

Paso 2: Aplicación de la Primera Forma Normal (1FN)

Analogía Didáctica: "El Casillero Postal Único". No puedes meter múltiples cartas desordenadas en un solo casillero. Cada celda de la tabla debe contener exactamente un solo valor indivisible (atómico) y crecer hacia abajo (en filas), no hacia los lados en listas o campos repetitivos.

Transformaciones:

  • Se extrae la lista de productos comprados generando una fila por cada ítem adquirido.
  • Se descompone el atributo compuesto nombre_cliente en primer_nombre y primer_apellido.
  • Se define una clave primaria compuesta que identifique unívocamente cada fila: (id_factura, id_producto).

Paso 3: Aplicación de la Segunda Forma Normal (2FN)

Analogía Didáctica: "Cada Dato con su Dueño Real". Cuando tienes una clave primaria compuesta, ningún dato descriptivo puede depender únicamente de un pedazo de la clave.

En (id_factura, id_producto): los datos del cliente y la fecha dependen exclusivamente de la id_factura. La descripción y el precio del producto dependen exclusivamente de id_producto. Solo la cantidad comprada depende de ambos.

Separación en 3 tablas:

  1. ordenes (id_orden [PK], fecha_orden, cedula_cliente, nombres, email...)
  2. productos (id_producto [PK], nombre_producto, categoria, precio_base, stock...)
  3. detalle_orden (id_orden [PK, FK], id_producto [PK, FK], cantidad, precio_venta) — Tabla asociativa que rompe la relación N:M.

Paso 4: Aplicación de la Tercera Forma Normal (3FN)

Analogía Didáctica: "Cero Teléfono Roto". Ningún campo no clave puede depender de otro campo no clave.

En la tabla ordenes, la dirección y teléfono dependían de la cédula del cliente (dependencia transitiva). En la tabla productos, la descripción de la categoría dependía del nombre de la categoría.

Resultado Final: Se aíslan las tablas maestras usuarios y categorias, y se crea la tabla transaccional transacciones para la pasarela electrónica.

5. Matriz de Relaciones y Cardinalidades (R1 a R6)

# Relación Tabla Origen Cardinalidad Tabla Destino Justificación de Negocio
R1 usuarios 1 : N ordenes Un usuario registrado puede generar cero o muchas órdenes de compra. Cada orden pertenece a un único usuario.
R2 categorias 1 : N productos Una categoría agrupa múltiples productos. Cada producto pertenece estrictamente a una categoría principal.
R3 ordenes 1 : N detalle_orden Una orden se compone de uno o más renglones de compra detallados.
R4 productos 1 : N detalle_orden Un producto puede estar presente en múltiples renglones de órdenes de distintos clientes.
R5 ordenes 1 : 1 transacciones Cada orden aprobada genera una única transacción electrónica vinculada mediante UNIQUE en id_orden.
R6 (Intermedia) ordenes N : M productos Relación muchos a muchos descompuesta formalmente mediante la tabla intermedia asociativa detalle_orden.

7. Guía Tutorial para la Evidencia EV02 (Diagrama CASE)

Pasos exactos para construir el diagrama formal en MySQL Workbench:

Paso 1 — Iniciar Modelo EER: Abre MySQL Workbench ➔ Menú File ➔ New Model (o Ctrl + N) ➔ Doble clic en "Add Diagram" para abrir el lienzo.
Paso 2 — Agregar las Tablas: Selecciona la herramienta Place a New Table (T) y haz clic en el lienzo. Define campos con marcas PK (Primary Key), NN (Not Null), UQ (Unique) y AI (Auto-Increment).
Paso 3 — Conectar las Relaciones: Usa la herramienta 1:n Non-Identifying Relationship (línea punteada) para unir categorias ➔ productos y usuarios ➔ ordenes. La pata de gallo apunta a la tabla hija.
Paso 4 — Exportar en Alta Resolución: Ve a File ➔ Export ➔ Export as PNG... o Export as PDF... Asegúrate de que las líneas no se crucen sobre el texto y que todas las claves sean 100% legibles.

8. Modelos de Conclusiones Técnicas & Normas APA

Modelos de Conclusiones Profesionales
1. Garantía de Integridad y Eliminación de Anomalías: La aplicación rigurosa de las tres primeras formas normales (1FN, 2FN y 3FN) permitió transformar la estructura plana original en un modelo relacional de seis entidades coherentes. Este proceso eliminó por completo las anomalías de inserción, actualización y borrado, asegurando que los datos de clientes y productos permanezcan consistentes aun cuando se modifiquen los históricos de órdenes. 2. Eficiencia en el Almacenamiento y Mantenimiento: Al aislar las dependencias transitivas en tablas maestras como categorias y transacciones, se reduce drásticamente el espacio de almacenamiento físico y se facilita la evolución futura del software, permitiendo incorporar nuevos métodos de pago o atributos descriptivos sin alterar las tablas centrales de facturación. 3. Escalabilidad y Preparación para el Desarrollo Backend: El diagrama Entidad-Relación construido en la herramienta CASE constituye el plano exacto para la ejecución del script SQL DDL durante la siguiente fase de desarrollo. La definición explícita de claves foráneas y reglas de integridad en cascada garantiza la robustez del sistema frente a transacciones concurrentes en el entorno web.

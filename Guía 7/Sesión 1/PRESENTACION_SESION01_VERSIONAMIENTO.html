Bloque 2 · Teoría y Contexto

Qué es el control de versiones y por qué lo necesitas

Entiende el problema antes de elegir la herramienta: así podrás justificar tu decisión con argumentos y no con gustos.

Problema

Sin control de versiones

Archivos como proyecto_final_v2_ahora_si.zip, cambios que se pisan entre compañeros y ningún rastro de quién rompió qué. Si algo falla, no tienes cómo volver atrás.

Solución

Con control de versiones

Cada cambio queda guardado como una versión (commit) con autor, fecha y mensaje. Puedes comparar, deshacer y trabajar en paralelo sin perder nada.

Beneficio

Lo que ganas en tu proyecto

Historial completo, ramas para probar ideas sin riesgo, colaboración ordenada y una base para la integración continua del componente formativo.

Idea clave para tu informe

Un sistema de control de versiones (VCS) registra los cambios de los archivos a lo largo del tiempo. En la introducción de tu informe puedes explicar esto en dos frases: qué problema resuelve (perder trabajo, pisarse cambios) y por qué tu proyecto lo necesita (varios módulos, varias personas o varias entregas).

Bloque 2 · Historia del Control de Versiones

Historia del control de versiones: de las copias a mano a Git

Cada herramienta apareció para arreglar el problema de la anterior. Entender ese recorrido te explica por qué hoy usas Git.

Desliza horizontalmente para ver toda la línea de tiempo.

Por qué te importa

Con CVS y Subversion todo dependía de un servidor central: si fallaba o te quitaban el acceso, el equipo quedaba bloqueado. Eso le pasó al kernel de Linux con BitKeeper, y por eso Git nació distribuido: cada persona tiene el historial completo en su computador.

En el siguiente slide verás la diferencia entre centralizado y distribuido.

Qué te llevas para tu informe EV01: puedes justificar que Git es el estándar porque resolvió la dependencia de un servidor central, y que GitHub o GitLab añaden la colaboración en la web.

Bloque 2 · Modelos de Versionamiento

Control de versiones centralizado vs distribuido

Esta comparación es la base para justificar por qué hoy casi todos los equipos usan Git. Úsala en la sección de selección de tu informe.

Centralizado (CVCS)

Un servidor, una sola fuente

Si el servidor cae: nadie puede guardar versiones ni consultar el historial.

Ejemplos: Subversion (SVN), CVS. Todos se conectan a un servidor único; si cae, nadie puede guardar versiones y el historial completo vive solo allí.

Distribuido (DVCS)

Cada copia es un repositorio completo

Si el remoto cae: cada equipo sigue trabajando con su historial completo.

Ejemplos: Git, Mercurial. Trabajas y haces commits sin conexión; el remoto sirve para compartir y respaldar, no para poder trabajar.

AspectoCentralizado (SVN)Distribuido (Git)
HistorialSolo en el servidorCompleto en cada copia local
Trabajo sin internetMuy limitadoTotal: commit, ramas e historial local
RamasPesadas y poco usadasBaratas y rápidas: base de los flujos modernos
Riesgo si falla el servidorAlto: punto único de fallaBajo: cada clon es un respaldo
Bloque 2 · Git, GitHub, GitLab y Bitbucket

Git no es GitHub: el motor y los hospedajes

Un error muy común en los informes es mezclar Git con GitHub. Distinguirlos ya te hace ver más profesional.

Herramienta

Git es el motor

Git es el sistema de control de versiones que instalas en tu computador y que guarda el historial de tu proyecto. Funciona por sí solo, sin internet.

Plataformas

GitHub, GitLab y Bitbucket son el hospedaje

Son servicios web que alojan tus repositorios Git y añaden colaboración: pull/merge requests, issues, revisiones y automatización. No son Git: son donde publicas tu Git.

Bloque 2 · Versionamiento Local y Remoto

Versionamiento local y remoto: tu computador y la nube

El primer indicador del instrumento te pide diferenciar con claridad lo local de lo remoto. Mira el dibujo: de un lado está tu equipo, del otro el servidor, y cuatro comandos mueven el trabajo entre ambos.

AspectoVersionamiento localVersionamiento remoto
Dónde viveEn tu computador, dentro de la carpeta .git de tu proyectoEn un servidor: GitHub, GitLab o Bitbucket
Necesita internetNo: puedes hacer commits, ramas y consultar el historial sin conexiónSí: solo para subir (push) o descargar (fetch, pull, clone)
Quién lo veSolo tú, hasta que lo publiquesTu equipo, el instructor y quien tenga permiso
Comandos típicosgit init, git add, git commit, git branch, git loggit clone, git push, git fetch, git pull
Para qué lo usasGuardar versiones de tu trabajo y poder volver atrásRespaldar, colaborar, revisar código (pull requests) y automatizar pruebas
Riesgo si solo tienes esteSi se daña tu disco, pierdes el historialSin copia local no puedes trabajar sin conexión ni hacer commits propios
Fetch y pull: la confusión más común

git fetch es como mirar el buzón: ves qué llegó, pero no tocas tus archivos. git pull es abrir el buzón y guardar lo que llegó en tu escritorio: trae y además mezcla los cambios con tu trabajo. Si dudas, haz primero fetch.

Error frecuente

Escribir "mi código está en Git" cuando solo está en GitHub, o al revés. Un commit existe primero solo en tu repositorio local; llega al remoto únicamente cuando haces git push.

Explica con tus palabras qué es cada uno, cuál herramienta cumple cada rol en tu proyecto (por ejemplo, Git como repositorio local y GitHub como remoto) y cómo viaja el trabajo entre ambos (clone, push, fetch, pull). Paso 0 · Instala Git (si aún no lo tienes)

Windows

Instalar Git en Windows

  1. Entra a git-scm.com/download/win y descarga el instalador (64-bit).
  2. Ejecútalo y pulsa Next. Cuando pregunte por el editor predeterminado, elige Visual Studio Code.
  3. Deja el resto de opciones por defecto (incluida la que permite usar Git desde la línea de comandos).
  4. Al terminar, abre Git Bash desde el menú Inicio y escribe git --version.
macOS

Instalar Git en macOS

  1. Abre la Terminal y escribe git --version.
  2. Si Git no está, macOS ofrece instalar las herramientas de línea de comandos: acepta y espera.
  3. Alternativa con Homebrew: brew install git.
  4. Vuelve a escribir git --version para confirmar.
Linux

Instalar Git en Linux

  1. Debian o Ubuntu: sudo apt update y luego sudo apt install git.
  2. Fedora: sudo dnf install git.
  3. Comprueba con git --version.
Antes de seguir
  • Crea tu cuenta gratuita en github.com con el correo que usarás también en git config.
  • Si no alcanzas a instalarlo hoy, no te detengas: seguirás la explicación del informe EV01 y lo instalamos paso a paso, con pantallazos, en la Sesión 3 (EV04).
  • Los pasos pueden variar un poco según la versión del instalador; lo importante es que git --version responda.

Bloque 3 · Demo en Vivo

El flujo de trabajo de Git de principio a fin

Entender este recorrido te permite explicar en tu informe por qué el versionamiento es parte de tu plan de trabajo y no un adorno.

02_flujo_basico_git.sh
Terminal · Git Bash
1# Crear el proyecto y arrancar el repositorio local
2$ mkdir techstore-pro
3$ cd techstore-pro
4$ git init
5Initialized empty Git repository in .../techstore-pro/.git/
6
7# Working dir -> staging -> commit
8$ echo "# TechStore Pro" > README.md
9$ git status
10Untracked files: README.md
11$ git add README.md
12$ git commit -m "docs: crea README inicial"
13[main (root-commit) 3f2a9c1] docs: crea README inicial
14
15# Asegura que la rama se llame main (según tu versión puede ser master)
16$ git branch -M main
17
18# Commit -> remoto (GitHub o GitLab)
19$ git remote add origin https://github.com/tu-usuario/techstore-pro.git
20$ git push -u origin main
Para ti: las cuatro zonas de Git

Tu cambio viaja por cuatro zonas: lo editas en el directorio de trabajo, lo marcas en staging con git add, lo guardas en tu repositorio local con git commit y lo compartes en el remoto con git push. Este mismo diagrama puedes incluirlo (o redibujarlo) en tu informe para explicar cómo trabajarás.

Nota: según tu versión, la rama inicial puede llamarse master o main. En la Sesión 4 (EV05) la guía usa master; si tu rama se llama distinto, adapta el comando.

Bloque 3 · Ejemplo Aplicado

TechStore Pro: por qué elegir Git + GitHub

Un caso completo de principio a fin para que veas cómo se pasa de las características del software a la selección de herramientas.

Contexto

TechStore Pro (proyecto ficticio)

Tienda en línea de tecnología con catálogo, carrito y pagos. Equipo de 3 aprendices, metodología Scrum con sprints de 2 semanas, código en Java con pruebas automáticas.

Necesidades

Qué exige el proyecto

Trabajo en paralelo por historia de usuario, revisión de código entre compañeros, pruebas automáticas en cada push y un historial que pruebe el avance de cada sprint.

Decisión

Git + GitHub + GitHub Flow

Git para versionar sin depender de internet, GitHub para pull requests e issues, GitHub Actions para integración continua y ramas feature/ por historia de usuario.

03_flujo_ramas_techstore.sh
Terminal · GitHub Flow

Selección de herramientas de versionamiento

Características del software: aplicación web en Java, equipo de 3 integrantes, entregas por sprint de dos semanas y necesidad de pruebas automáticas.

Alternativas analizadas: Subversion (centralizado) y Git (distribuido), alojados en GitHub, GitLab o Bitbucket. Se evaluaron facilidad de uso, integración continua, colaboración, costo, comunidad y coherencia con los componentes formativos.

Herramientas seleccionadas:

"Se selecciona Git como sistema de control de versiones por ser distribuido: cada integrante conserva el historial completo y puede trabajar sin conexión. Se selecciona GitHub como plataforma remota por sus pull requests para revisar el código de cada historia de usuario y por GitHub Actions, que permite ejecutar las pruebas en cada push, en coherencia con el componente de Integración continua. Se adopta GitHub Flow, con ramas feature/ por historia de usuario, porque se ajusta a los sprints cortos de Scrum."
Ejemplo · Conclusiones y referencias

Conclusiones y referencias

"La combinación de Git y GitHub responde a las necesidades de colaboración, trazabilidad e integración continua de TechStore Pro. La decisión se documenta para que el equipo pueda mantener un flujo de trabajo ordenado durante todo el ciclo del proyecto."

Referencias sugeridas: Documentación oficial de Git (git-scm.com), documentación de GitHub (docs.github.com), documentación de GitLab (docs.gitlab.com) y los materiales de los componentes formativos de la Guía 7.

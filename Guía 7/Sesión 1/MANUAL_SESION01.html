Compara las herramientas de versionamiento

Tiempo estimado: 25 min

Aquí está el corazón del informe. Debes comparar dos niveles que mucha gente confunde:

Sistema de control de versiones (SCV): el programa que registra los cambios. Ejemplos: Git, Subversion (SVN), Mercurial. Se instala en tu computador.
Plataforma de alojamiento remoto: el sitio web donde guardas una copia en la nube y colaboras. Ejemplos: GitHub, GitLab, Bitbucket. Git es el programa; GitHub es el servicio.

Introducción (2 párrafos)

Introducción (modelo)
Todo proyecto de software cambia constantemente: se agregan funciones, se corrigen errores y varias personas editan los mismos archivos. Sin un control ordenado de esos cambios es fácil perder trabajo, pisar el código de un compañero o no poder volver a una versión que funcionaba. Los sistemas de control de versiones resuelven este problema porque registran cada cambio, quién lo hizo y cuándo, y permiten regresar a cualquier punto del historial. Este informe presenta el plan de trabajo en versionamiento del proyecto TechStore Pro, una tienda en línea de tecnología. El documento describe el proyecto, compara los principales sistemas de control de versiones (Git, Subversion y Mercurial) y las plataformas de alojamiento remoto (GitHub, GitLab y Bitbucket), y selecciona con argumentos la herramienta que se usará durante el desarrollo. También describe las herramientas de desarrollo para la codificación y explica la diferencia entre el versionamiento local y el remoto. Al final se presentan las conclusiones y las fuentes consultadas.

Fíjate en la fórmula: el primer párrafo explica el problema (por qué se necesita versionar) y el segundo dice qué contiene el informe.

Herramientas de desarrollo para la codificación 4.1 Editor o IDE y lenguaje de programación Para escribir el código de TechStore Pro el equipo usará Visual Studio Code, un editor gratuito y extensible que integra terminal, depurador y control de versiones con Git en una sola ventana. Explica el versionamiento local y el remoto

Tiempo estimado: 20 min

El indicador 1 del instructor pide que diferencies con claridad el versionamiento local del remoto. Mucha gente cree que Git y GitHub son lo mismo; no lo son. Tu informe debe dejar claro qué ocurre en tu computador y qué ocurre en el servidor.

Versionamiento local: el historial de cambios vive en tu computador. Guardas versiones (commits), creas ramas y vuelves atrás sin internet. Lo hace Git.
Versionamiento remoto: una copia del repositorio vive en un servidor (GitHub, GitLab, Bitbucket). Sirve para respaldar, compartir y revisar código en equipo. Necesita internet.

4.2 Entorno de ejecución y gestor de paquetes

El back-end se ejecuta sobre Node.js, el entorno que permite correr JavaScript fuera del navegador, y se construye con Express para definir las rutas de la API. El front-end se desarrolla con React. Las librerías (por ejemplo express, mongoose y react) se instalan y actualizan con npm, el gestor de paquetes que viene con Node.js, y quedan registradas en el archivo package.json para que cualquier integrante pueda reproducir el mismo entorno en su equipo.

4.3 Base de datos y herramientas de depuración

La información del catálogo, los usuarios y los pedidos se guarda en MongoDB, una base de datos de documentos cuyo formato es muy parecido a JSON, el mismo formato que usa JavaScript, y que facilita cambiar la estructura de los datos durante un desarrollo ágil. Para encontrar errores se usará el depurador integrado de Visual Studio Code en el back-end, las herramientas para desarrolladores (DevTools) de Chrome en el front-end y Postman para probar las rutas de la API sin esperar a que la interfaz esté lista.

La combinación de MongoDB, Express, React y Node.js (stack MERN) se eligió porque todo el proyecto se programa en un solo lenguaje y porque cada pieza tiene documentación abundante y versión gratuita.

5. Versionamiento local y remoto

5.1 Qué es cada uno

El versionamiento local es el que ocurre en el computador de cada integrante: Git guarda en una carpeta oculta del proyecto (.git) el historial completo de cambios y permite confirmar versiones (commit), crear ramas y volver a estados anteriores sin conexión a internet. El versionamiento remoto ocurre en un servidor, en este caso GitHub, donde se aloja una copia compartida del repositorio. Sirve para respaldar el trabajo, sincronizar al equipo y revisar el código de los compañeros mediante pull requests.

5.3 Flujo de trabajo entre el repositorio local y el remoto

  1. clone: cada integrante descarga a su equipo una copia del repositorio remoto de TechStore Pro.
  2. add: selecciona los archivos modificados que entrarán en la próxima versión.
  3. commit: guarda esa versión en el historial local con un mensaje claro.
  4. push: envía los commits locales al repositorio remoto en GitHub.
  5. pull: trae al equipo local los cambios que subieron los compañeros.

Los pasos add y commit son locales y funcionan sin internet; clone, push y pull necesitan conexión porque se comunican con el remoto.

6. Conclusión

Después de analizar las características de TechStore Pro y de comparar las herramientas disponibles, se concluye que Git es la opción más adecuada para versionar el proyecto, porque combina trabajo sin conexión, ramas ligeras y una comunidad muy amplia. GitHub complementa a Git como plataforma remota, ya que ofrece repositorios gratuitos, revisión de código mediante pull requests y automatización con GitHub Actions.

Usar un sistema de control de versiones desde el primer día reduce el riesgo de perder trabajo, facilita que el equipo colabore sin pisarse y deja un historial que permite volver a una versión estable. Como siguiente paso del plan de trabajo, se instalará y configurará Git en cada equipo, se creará el repositorio remoto y se definirán los estándares de codificación del proyecto.

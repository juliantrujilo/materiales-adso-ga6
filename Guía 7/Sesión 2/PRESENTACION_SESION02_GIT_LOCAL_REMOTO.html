Bloque 2 · Teoría y Contexto

Dos lugares, una misma historia: el mapa de hoy

Antes de memorizar comandos, mira el mapa completo. Todo lo de hoy se reduce a entender estos dos lugares y las cuatro flechas que los conectan.

Local

Git local: tu cuaderno de trabajo

Es el repositorio que vive en tu computador, dentro de la carpeta oculta .git. Ahí guardas tus versiones (commits) sin necesitar internet. Es tuyo: nadie más lo ve hasta que tú lo compartas.

Remoto

Git remoto: la pizarra compartida del equipo

Es una copia del proyecto alojada en un servidor (GitHub). Sirve para compartir, respaldar y colaborar: todo el equipo sube y baja cambios desde ahí.

Analogía: cuaderno y pizarra

Piensa en un trabajo en grupo: cada uno escribe en su cuaderno (repositorio local) y, cuando algo está listo, lo copia en la pizarra compartida (repositorio remoto) para que los demás lo vean. Si un compañero actualiza la pizarra, copias sus cambios a tu cuaderno. Los comandos push y pull son esa copia en cada sentido.

Error frecuente

Decir que "Git" y "GitHub" son lo mismo. Git es la herramienta que registra versiones; GitHub es un servicio donde se aloja el repositorio remoto. Git funciona perfectamente sin GitHub; GitHub no funciona sin Git.

Qué te llevas para tu informe EV03: la idea central de tu introducción: tu proyecto tiene una copia local donde trabajas y una copia remota donde colaboras, conectadas por comandos concretos.

Bloque 2 · Características de Git local

Características del versionamiento local

El segundo indicador te pide describir las características de las herramientas locales. Estas son las que debes saber nombrar y explicar.

Ubicación

Vive en tu equipo

El repositorio es la carpeta oculta .git dentro de tu proyecto. Contiene todo el historial: cada commit, cada rama y los metadatos.

Disponibilidad

No necesita internet

add, commit, log, status, diff y branch funcionan sin conexión, y son muy rápidos porque no consultan a nadie.

Historial

Historial completo y trazable

Cada commit guarda autor, fecha y mensaje. Puedes ver qué cambió, comparar versiones y volver a un estado anterior.

Alcance

Privado por defecto

Solo tú ves lo que hay en tu repositorio local. Nadie más recibe tus cambios hasta que los publiques en un remoto.

Ramas

Ramas para experimentar

Puedes crear ramas con git branch para probar ideas sin tocar la versión principal y unirlas después.

Límite

No es una copia de seguridad

Si tu disco se daña o borras la carpeta, pierdes el historial. Por eso necesitas un remoto que guarde una copia fuera de tu equipo.

Ejemplo real: TechStore Pro sin conexión

Laura viaja en bus sin datos móviles. Aun así modifica el carrito de compras, hace git add y git commit -m "Agrega carrito". Todo queda registrado en su repositorio local. Cuando tenga internet, hará git push para compartirlo con el equipo.

Qué te llevas para tu informe EV03: una sección Características del versionamiento local con al menos cinco: ubicación, uso sin internet, historial completo, ramas y privacidad, más su limitación (indicador 2).
Bloque 2 · Características de Git remoto

Características del versionamiento remoto

El tercer indicador te pide describir las características de las herramientas remotas. Fíjate que aquí aparece lo que el repositorio local no puede darte.

Ubicación

Alojado en un servidor

Vive en GitHub. Se identifica con una URL (https o SSH) y recibe un nombre corto en tu proyecto; por convención, origin.

Colaboración

Compartido con tu equipo

Varias personas suben y bajan cambios del mismo repositorio. Los permisos definen quién puede leer, escribir o administrar.

Respaldo

Copia fuera de tu equipo

Si tu computador falla, el proyecto sigue en la nube y lo recuperas con git clone.

Sincronización

Se actualiza con push y pull

Envías tus commits con git push y recibes los de otros con git pull o git fetch. Requiere internet.

Herramientas extra

Pull requests e issues

Las plataformas añaden revisión de código, seguimiento de tareas (issues), wikis y automatización con CI/CD.

Límite

Depende de la red y de los permisos

Sin internet no puedes subir ni bajar cambios, y sin permiso de escritura tu push será rechazado.

Ejemplo real: Mateo revisa el trabajo de Laura

Laura hace git push y su rama aparece en GitHub. Mateo abre un pull request, comenta el código y, cuando todo está bien, el equipo lo une a la rama principal. Esa revisión solo existe en el remoto.

Qué te llevas para tu informe EV03: una sección Características del versionamiento remoto que nombre GitHub, su URL de ejemplo, la colaboración, el respaldo y la sincronización (indicador 3).

Bloque 2 · Cómo se conectan

Cómo se conectan: el ciclo de trabajo diario

Local y remoto no compiten: se turnan. Este es el ciclo que repetirás cada día cuando trabajes con tu equipo.

  1. Empiezas el día con git pull. Traes lo que tus compañeros subieron mientras no estabas. (Remoto → local)
  2. Trabajas en tu editor. Modificas archivos en el directorio de trabajo. (Solo local)
  3. Revisas con git status. Ves qué cambió y qué falta preparar. (Solo local)
  4. Preparas con git add y guardas con git commit. Cada commit es una versión con mensaje. (Solo local)
  5. Compartes con git push. Tus commits suben al repositorio remoto. (Local → remoto)
Por qué el orden importa

Si haces push sin haber hecho pull y un compañero ya subió cambios, el remoto rechaza tu envío porque tu historial quedó atrás. Empezar con pull evita ese conflicto y es la razón de que el ciclo empiece ahí.

Error frecuente

Creer que git commit sube el código a GitHub. El commit solo guarda la versión en tu repositorio local; únicamente git push la envía al remoto.

Qué te llevas para tu informe EV03: un párrafo que explique este ciclo con tus palabras: qué ocurre solo en el repositorio local, qué comandos lo conectan con el remoto y en qué orden se usan.

Para ti: qué error previene cada comando
  • git remote -v confirma la URL antes de que un push falle por un enlace mal escrito.
  • origin es solo el nombre convencional del remoto; la guía de la EV05 usa github y la rama master. Puedes elegir el nombre del remoto, pero debes usar el mismo en push y pull.
  • La rama inicial puede llamarse master o main según tu versión de Git. Mira cuál tienes con git branch y usa ese nombre en push y pull; el comando git branch -M main la renombra a main.
  • fetch te deja mirar antes de unir; pull es fetch más la unión.
  • Para subir al remoto, GitHub te pedirá autenticarte; lo configuras paso a paso en la Sesión 3 (EV04).
Importante

No ejecutes estos comandos con un repositorio remoto ajeno. En esta sesión puedes leer y entender cada comando; la práctica completa con el repositorio Programa-Git es la EV05 (Sesión 4).

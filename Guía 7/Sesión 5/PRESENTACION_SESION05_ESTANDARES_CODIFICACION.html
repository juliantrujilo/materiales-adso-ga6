Bloque 2 · Qué es un estándar y por qué importa

Un estándar de codificación es el acuerdo del equipo sobre cómo se escribe el código

No cambia lo que hace el programa: cambia lo fácil que es leerlo, revisarlo y mantenerlo entre varias personas.

Sin estándar

El equipo de TechStore Pro, semana 1

Laura escribe calc_total, Camilo escribe CalcularTotal y Andrea escribe ct. Cada archivo tiene otra indentación y otro tipo de comillas. En la revisión nadie entiende el código del otro y, al unir ramas con Git, aparecen conflictos que son solo de formato.

Con estándar

El mismo equipo, semana 3

Acuerdan un documento de una página: funciones en camelCase, clases en PascalCase, 2 espacios, comillas simples. Un formateador aplica el formato solo y un linter avisa los errores. Las revisiones se centran en la lógica, no en el estilo.

BeneficioQué significa en la práctica
LegibilidadCualquiera del equipo entiende el código sin preguntar
MantenimientoCorregir o ampliar el programa cuesta menos tiempo
Menos erroresReglas como const en vez de var evitan fallos típicos
Trabajo en equipo con GitMenos conflictos por formato y revisiones más cortas
Dónde sale el estándar

Un equipo no inventa todo desde cero: adopta una guía oficial (Google, Airbnb, PSR-12…) y documenta sus decisiones propias. Las reglas de hoy vienen de esas guías y las referencias están en el slide 14. Lo que es convención del equipo (por ejemplo, identificadores en inglés y comentarios en español) lo marcamos como tal.

Qué te llevas para tu informe EV02: la introducción de tu informe puede usar este caso: qué problema resuelve un estándar y por qué lo necesita tu proyecto (TechStore Pro u otro).

Bloque 2 · Declaración de clases

Declaración de clases: sustantivos en PascalCase y una responsabilidad por clase

La guía te pide explícitamente el estándar de declaración de clases. Una clase representa una cosa del problema: Producto, Carrito, Cliente.

  • Nombre en PascalCase (ProductItem), en singular y como sustantivo. Google lo llama UpperCamelCase.
  • Un archivo, una clase y el archivo se llama como la clase (ProductItem.js): así se encuentra sin buscar. En PHP, PSR-1 también exige una clase por archivo.
  • Propiedades y métodos en camelCase y con nombres completos (name, price), no n ni p.
  • Una responsabilidad: si el nombre necesita «y» (ProductAndCart), probablemente son dos clases.
  • Constructor corto: solo asigna datos; la lógica va en métodos.
clase_mal.js
MAL
1class product_item {
2 constructor(n, p) {
3 this.n = n;
4 this.p = p;
5 }
6}
7const item = new product_item('Mouse', 45000);
clase_bien.js
BIEN
1class ProductItem {
2 constructor(name, price) {
3 this.name = name;
4 this.price = price;
5 }
6}
7const item = new ProductItem('Mouse', 45000);
Y en otros lenguajes

En Java la clase también es UpperCamelCase y los nombres de paquete van en minúscula, sin guion bajo. En PHP, PSR-1 usa StudlyCaps y las llaves de la clase van en la línea siguiente. Lo ves comparado en el slide 10.

Bloque 2 · Comentarios y documentación

Comentarios: explican el porqué; la documentación explica cómo usar el código

Un comentario que repite el código sobra. Uno que explica una decisión o documenta una función es oro para quien lo hereda.

Sí comentas

Lo que el código no dice

Por qué tomaste una decisión, una restricción del negocio (por ejemplo «el IVA es 19 %») y la documentación de cada función pública: qué recibe, qué devuelve y qué errores lanza.

No comentas

Lo obvio

// suma 1 a i repite la línea de abajo. Tampoco dejes código viejo comentado: para eso existe Git y su historial.

Bloque 3 · Herramientas que hacen cumplir el estándar

Linter y formateador: que la máquina revise lo que las personas olvidan

Un estándar escrito en un documento se olvida. Un estándar que una herramienta revisa cada vez que guardas o haces commit se cumple.

PlataformaFormateadorLinter o verificador de estiloQué revisan
JavaScript / Node.js / ReactPrettierESLintPrettier: comillas, espacios, saltos de línea. ESLint: var, nombres, variables sin usar, errores probables
Javagoogle-java-formatCheckstyleReglas de la Google Java Style Guide (nombres, Javadoc, llaves)
PHPPHP-CS-Fixer o PHP_CodeSniffer (phpcbf)PHP_CodeSniffer (phpcs)Cumplimiento de PSR-12 y PSR-1
Diferencia entre linter y formateador

El formateador reescribe el aspecto del código (espacios, comillas). El linter analiza el código y avisa de errores y de reglas rotas (por ejemplo, un nombre que no está en camelCase). Se usan juntos.

Dónde entra Git

Estas herramientas se guardan en el repositorio (package.json, eslint.config.mjs, .prettierrc). Así todo el equipo, al hacer git pull, recibe las mismas reglas. Es una buena razón para conectar este tema con tu informe de versionamiento.

Qué te llevas para tu informe EV02: una tabla corta con la herramienta de tu plataforma que verifica el estándar y qué revisa. Esto cuenta como herramienta de desarrollo en tu informe.

1.3 Versionamiento local y remoto

"El versionamiento local ocurre en el equipo del desarrollador: Git guarda el historial de cambios en una carpeta oculta del proyecto y funciona sin internet. El versionamiento remoto ocurre en un servidor: GitHub aloja una copia del repositorio para respaldarla y compartirla con el equipo. Se conectan con comandos como git remote add y git push."
